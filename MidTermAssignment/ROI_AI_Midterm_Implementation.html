1. My ROI idea from the discussion board

Original "ROI for AI" discussion post:
"Enterprise sales engineers lose substantial time manually searching through fragmented technical documentation to answer repetitive enterprise RFPs, creating a bottleneck that limits deal flow.

An internal GenAI engine indexed on past winning proposals can automatically draft verified answers to routine questions, freeing engineers to focus solely on expert review while enabling the business to pursue far more bids with existing staff."

The return comes from two places: engineers spend fewer hours searching for material they have already written, and the same team can respond to more bids.

2. What I implemented for this midterm

I built the search part of the idea. An engineer types in a requirement and gets back the 50 closest matching notices, ranked by Word2Vec similarity. The notebook does not draft answers, so this report only makes claims about search.

3. Dataset

  • Source: EuroTender, public procurement notices from the EU's Tenders Electronic Daily, published on Hugging Face as sinceaihq/eurotender-cpv under CC-BY 4.0.
  • Subset: 15,952 competition notices listed as English, published from October 2025 to September 2026 and saved as rfp_ted_notices.csv. Removing repeated titles leaves 15,540.
  • Coverage: all kinds of procurement, not only IT: 8,618 services, 5,368 supplies and 1,966 works notices.
  • Why it is a stand-in: these notices are written by buyers, not vendors. Real proposals are private, so I use the notices in place of a company's own proposal archive. The method would be the same on the real archive.

4. How the notebook works

The notebook follows the professor's template and ran on Apache Spark 4.0.4 in Google Colab.

Step Spark component What it does
1. Load and clean spark.read.csv() with escape='"', filter(), dropDuplicates(['title']) Loads 15,952 rows, keeps rows with a description (none were empty) and keeps each title once, leaving 15,540.
2. Tokenize and remove stopwords RegexTokenizer(pattern=r'\w+'), StopWordsRemover Splits description into lowercase words and removes stopwords, reducing 1,309,699 tokens to 833,258 (36.4% removed).
3. Train the model Word2Vec(vectorSize=100, minCount=5, maxIter=10, seed=42) Uses Skip-Gram: each word is used to predict the words around it, and the weights learned while doing this become the word vectors.
4. Turn text into vectors model.transform() Averages the word vectors of each notice and of the search query into one 100-number vector.
5. Rank cossim(), orderBy(), show(50) Scores the query against all 15,540 notices using cosine similarity and shows the top 50 titles.
Cosine similarity: similarity(q, d) = (q · d) / (‖q‖ × ‖d‖), where q is the query vector and d is the notice vector.

Where I changed the template

  • Reading the CSV: added escape='"', because the text in this file writes quotes as "".
  • Repeated titles: removed them because the result is a list of titles, so each should appear once.
  • Training: raised maxIter from the default of 1 to 10, because one pass underfit the data (see section 5), and fixed the seed.
  • Search scope: used every notice instead of the template's 30,000-row limit, because the dataset is small enough.

Keyword check

The data has no labels saying which notice answers which query, so I use a simple check. Each query gets a list of topic terms, and a notice counts as relevant if its title or description contains one of them. Precision at 50 is the share of the top 50 that are relevant. Base rate is the share of all notices that are relevant, which is what picking at random would give on average. Lift is precision divided by base rate. I chose the terms myself, so this is a rough measure.

6. What this means for the ROI

The results support using this search as a shortlist for an engineer to review, not as a final answer. On the strongest query, about 31 of the 50 titles were on topic; on the weakest, 5 to 9 were. An engineer would still need to check each result.

This midterm does not measure time saved or extra bids won, so I do not claim a financial figure. To work out the return, a company would run a pilot on its own proposal archive and measure the values in this calculation:

Yearly benefit = (search hours saved per RFP × RFPs per year × hourly cost of an engineer) + (extra bids per year × win rate × margin per win)

ROI = (yearly benefit − yearly cost of the system) / yearly cost of the system

7. Limits

  • Averaging word vectors loses the meaning of a word in context. "Security" also brings in guarding and travel risk notices, and the data protection query returned "Vulnerability Assessments to International Protection Applicants".
  • A high similarity score does not guarantee a relevant notice, so the scores cannot be read as a measure of quality.
  • These notices are requests from buyers, so the search finds similar requirements, not past answers. To reuse past answers, the same method would have to run on a company's own proposals.
